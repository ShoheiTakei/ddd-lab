# STEP 11 — 統合シナリオ

## ゴール

設計書 7 章のシナリオ S-01〜S-08 をそのままテストにして、
**設計が仕様を語れているか**を検証する。
シナリオを書くのに不自然な回り道が要るなら、モデルが間違っている。

## 要件

### 受入テスト

`test/scenario/` に 1 シナリオ 1 ファイル。
リポジトリはインメモリ実装を使い、ユースケース経由で操作する。
ドメインオブジェクトを直接いじって近道しない。

| ファイル | シナリオ |
|---|---|
| `s01_happy_path_test.dart` | 希望提出から確定まで |
| `s02_submit_after_deadline_test.dart` | 締切後の希望提出 |
| `s03_minor_at_night_test.dart` | 18 歳未満を深夜番に割当 |
| `s04_understaffed_test.dart` | 最低人数を満たさない |
| `s05_weekly_hours_exceeded_test.dart` | 週 40 時間超過 |
| `s06_outside_request_test.dart` | 希望外の枠への割当 |
| `s07_modify_confirmed_test.dart` | 確定済みシフトの変更試行 |
| `s08_unconfirm_and_edit_test.dart` | 確定取消して再編集 |

各シナリオは設計書に書かれた「期待結果」まで検証すること。
たとえば S-04 なら、不足している日・枠・必要人数・現在人数が
`Violation` から読み取れることを assert する。

### テストデータ

`test/scenario/fixtures.dart` にシナリオ用のスタッフとシフト表の組み立てを置く。
S-01 が通る「正常な半月分の割当」を 1 つ作り、他のシナリオはそれを**崩して**使う。
違反を 1 つだけ作る形にすると、何を検証しているかが明確になる。

### CLI

`bin/ddd_lab.dart` で S-01 を最初から最後まで実行し、
各段階（希望提出 / 割当 / 検査結果 / 確定）を標準出力に表示する。

- 引数なしで `dart run` するだけで動くこと。
- 途中で違反を 1 つ混ぜたパターンを `dart run bin/ddd_lab.dart --violate` で出せるようにする。
- 出力整形のためのパッケージは入れない。

## 禁止事項

- テスト内でドメインの private に触ること。
- シナリオを通すためのドメイン側の抜け道追加（テスト専用メソッドなど）。
  通らないならモデルを直す。
- 対話的な CLI、引数パーサのパッケージ。

## 完了条件

- 上記 8 ファイルが全て通る。
- `dart run bin/ddd_lab.dart` が確定まで到達する。
- `dart run bin/ddd_lab.dart --violate` が違反を表示し、確定に失敗する。
- `dart analyze` 警告 0。
