# コンビニ シフト管理 — ドメイン設計

作成日: 2026-09-12
ステータス: 要件定義・設計フェーズ（実装なし）

図面は [diagrams.md](./diagrams.md) を参照。

---

## 1. 目的とスコープ

DDD の戦術パターンを学習するための題材として、コンビニエンスストアのアルバイト
シフト管理を扱う。

### スコープ内（コア）

スタッフの希望提出から、店長によるシフト確定まで。

1. スタッフがシフト希望を提出する
2. 店長が希望をもとに手動で割当を作成する（ドラフト）
3. システムが労基法・店舗運営ルールへの違反を検査する
4. 違反がなければ店長がシフトを確定する

### スコープ外

- 確定後のシフト交代・欠勤申請
- 勤怠打刻、予定と実績の差分管理
- 給与計算、深夜割増の金額計算
- 複数店舗のヘルプ勤務

スコープ外の項目は、境界づけられたコンテキストとしては存在するものとして扱うが、
本設計では中身を定義しない（コンテキストマップ上に外部として置くのみ）。

### 設計方針

- 割当の生成はしない。店長が手で割り当て、システムは**検査する側に回る**。
  最適化アルゴリズムではなく、不変条件とルール表現の学習が目的のため。
- 実装言語は未定。本フェーズは要件定義と図面まで。

## 2. ユビキタス言語

| 用語 | 英語 | 定義 |
|---|---|---|
| 店舗 | Store | シフトを管理する単位。本設計では単一店舗を前提とする |
| スタッフ | Staff | 店舗に所属するアルバイト従業員 |
| 店長 | Manager | シフトを作成・確定する権限を持つ者 |
| シフト枠 | ShiftSlot | 1日を区切る固定の勤務区分。早番・中番・遅番・深夜番の4種 |
| シフト日 | ShiftDate | 対象となる暦日 |
| シフト希望 | ShiftRequest | スタッフが提出する、勤務可能な枠の申告 |
| 割当 | ShiftAssignment | 「ある日・ある枠・あるスタッフ」の組。シフトの最小単位 |
| シフト表 | ShiftSchedule | 1店舗・1対象期間分の割当の集合 |
| 対象期間 | SchedulePeriod | シフト表が対象とする期間。半月単位（1日〜15日 / 16日〜末日） |
| 提出締切 | RequestDeadline | 希望提出を受け付ける期限 |
| 確定 | Confirm | シフト表を正式版とし、以降の変更を禁止する操作 |
| 違反 | Violation | ルールに反した割当状態。種別と対象を持つ |
| レジ研修修了 | RegisterCertified | レジ操作の研修を修了した状態。人員要件で参照される |

**シフト枠の定義**

| 枠 | 時間帯 | 深夜区分 |
|---|---|---|
| 早番 | 06:00 - 12:00 | - |
| 中番 | 12:00 - 18:00 | - |
| 遅番 | 18:00 - 22:00 | - |
| 深夜番 | 22:00 - 06:00（翌日） | 深夜 |

深夜番は日付をまたぐ。深夜番の所属日は**開始日**とする。

## 3. ビジネスルール（不変条件）

確定時に全て満たされている必要がある。ドラフト状態では違反を保持したまま編集できる。

### 労基法系

| ID | ルール | 備考 |
|---|---|---|
| R-01 | 18歳未満のスタッフを深夜番に割り当ててはならない | 労基法61条相当。22時以降の就労禁止 |
| R-02 | 1人のスタッフの週あたり労働時間は40時間を超えてはならない | 週の起点は月曜 |
| R-03 | 1人のスタッフの連続勤務日数は6日を超えてはならない | 週1日の法定休日を確保する |
| R-04 | 深夜番の翌日、同一スタッフを早番・中番に割り当ててはならない | 勤務間インターバルの確保 |

### 店舗運営系

| ID | ルール | 備考 |
|---|---|---|
| R-05 | 各シフト枠には最低2名を割り当てなければならない | 深夜番も2名 |
| R-06 | 各シフト枠に、レジ研修修了者を1名以上含まなければならない | |
| R-07 | 同一スタッフを同一日の同一枠に重複して割り当ててはならない | |
| R-08 | スタッフが希望を出していない枠に割り当ててはならない | 希望外割当の禁止 |

### 期間・状態系

| ID | ルール | 備考 |
|---|---|---|
| R-09 | 提出締切を過ぎた後のシフト希望は受け付けない | |
| R-10 | 確定済みのシフト表は変更できない | 変更するには確定を取り消す |
| R-11 | 違反が1件でも残っているシフト表は確定できない | |

### ルールの分類

- **R-01, R-04, R-07** は割当1件、または割当2件の関係のみで判定できる。
- **R-02, R-03, R-05, R-06** は対象期間の割当全体を見ないと判定できない。
  → この事実が集約境界を決める（第4章）。
- **R-08** はシフト希望（別集約）を参照する。
  → 集約をまたぐため、アプリケーション層で希望を読み込んでからドメインに渡す。

## 4. 集約境界

### 決定: 対象期間を集約とする

`ShiftSchedule`（1店舗 × 1対象期間）を集約ルートとし、`ShiftAssignment` を
その内部エンティティとして保持する。

**理由**

R-02（週40時間）、R-03（連続勤務日数）、R-05（最低人数）、R-06（レジ研修者）は、
いずれも「対象期間内の全割当」を見なければ判定できない。集約とは不変条件を守れる
一貫性の境界であり、判定に必要な情報の範囲とトランザクション境界を一致させるなら、
対象期間そのものが集約になる。

割当を単独の集約ルートにすると、これらのルールが集約をまたぎ、ドメインサービスと
結果整合で担保することになる。学習の初手としては境界が曖昧になりすぎる。

**トレードオフ**

対象期間が半月・4枠・各2名なら、割当は最大で 15日 × 4枠 × 数名 ≒ 100〜200件。
集約としては大きい部類だが、半月で区切ることで上限が明確に抑えられている。
1か月や1年を1集約にすると破綻する。

期間を半月にしたのは、この上限を設計上の定数にするため。

### 集約一覧

| 集約ルート | 内部エンティティ | 主な責務 |
|---|---|---|
| `ShiftSchedule` | `ShiftAssignment` | 割当の追加・削除、全ルールの検査、確定 |
| `ShiftRequest` | なし | スタッフ1名 × 1対象期間の希望枠の集合。締切判定 |
| `Staff` | なし | 氏名、生年月日、レジ研修修了フラグ、在籍状態 |

`Staff` と `ShiftRequest` は `ShiftSchedule` から **ID で参照する**。オブジェクト
参照は持たない。

### 集約をまたぐ判定の扱い

R-01（18歳未満の深夜禁止）と R-06（レジ研修者）は `Staff` の属性を必要とするが、
`Staff` は別集約である。`ShiftSchedule` が `Staff` を直接読むと境界を壊す。

対応: 判定に必要な最小限の情報だけを値オブジェクト `StaffProfile`
（`staffId` / `isMinor` / `isRegisterCertified`）にコピーし、検査メソッドの引数として
外から渡す。アプリケーション層が `StaffRepository` から読み、`StaffProfile` に
変換して渡す。

これは「集約は他集約の状態のスナップショットを引数で受け取ってよい」という形。
`ShiftSchedule` は `Staff` の存在を知らず、判定に必要な述語だけを知る。

## 5. モデル構成要素

### 値オブジェクト

| 名前 | 構成 | 責務 |
|---|---|---|
| `StaffId` | UUID | 同一性 |
| `StoreId` | UUID | 同一性 |
| `ScheduleId` | UUID | 同一性 |
| `ShiftSlot` | 列挙（早番/中番/遅番/深夜番） | 時間帯と労働時間の保持、深夜判定 |
| `ShiftDate` | 日付 | 暦日 |
| `SchedulePeriod` | 開始日・終了日 | 半月の妥当性検証、含有判定、週単位への分割 |
| `WorkingHours` | 時間数 | 加算、上限比較 |
| `StaffProfile` | staffId / isMinor / isRegisterCertified | 他集約の状態のスナップショット |
| `Violation` | 種別 / 対象日 / 対象枠 / 対象スタッフ / メッセージ | 違反1件の表現 |

`ShiftSlot` は単なる列挙ではなく、`workingHours()` と `isLateNight()` を持つ。
「深夜かどうか」の知識を枠自身に閉じ込め、呼び出し側で時刻を比較させない。

### エンティティ

| 名前 | 同一性 | 属性 |
|---|---|---|
| `ShiftSchedule`（集約ルート） | `ScheduleId` | storeId / period / status / assignments |
| `ShiftAssignment` | date + slot + staffId | date / slot / staffId |
| `ShiftRequest`（集約ルート） | staffId + period | staffId / period / 希望枠の集合 / 提出日時 |
| `Staff`（集約ルート） | `StaffId` | 氏名 / 生年月日 / レジ研修修了 / 在籍状態 |

### ドメインサービス

| 名前 | 責務 |
|---|---|
| `ShiftRuleChecker` | 全ルールを順に適用し `Violation` のリストを返す |

個別ルールは `ShiftRule` インターフェースの実装として分割する（仕様パターン）。
`ShiftRuleChecker` はそれらを束ねるだけ。ルールの追加が既存コードの変更にならない。

### ドメインイベント

| イベント | 発生タイミング | 含む情報 |
|---|---|---|
| `ShiftRequestSubmitted` | 希望提出時 | staffId / period / 希望枠 |
| `ShiftAssignmentAdded` | 割当追加時 | scheduleId / date / slot / staffId |
| `ShiftAssignmentRemoved` | 割当削除時 | 同上 |
| `ShiftScheduleConfirmed` | 確定時 | scheduleId / storeId / period / 確定日時 |
| `ShiftScheduleUnconfirmed` | 確定取消時 | scheduleId / 理由 |

`ShiftScheduleConfirmed` はスコープ外コンテキスト（通知、勤怠）への連携点になる。
本設計では発行するところまでを定義し、購読側は定義しない。

### リポジトリ

| 名前 | 操作 |
|---|---|
| `ShiftScheduleRepository` | findById / findByStoreAndPeriod / save |
| `ShiftRequestRepository` | findByStaffAndPeriod / findByPeriod / save |
| `StaffRepository` | findById / findByIds / findActiveByStore |

集約ごとに1リポジトリ。`ShiftAssignment` 専用のリポジトリは作らない。

## 6. シフト表の状態

| 状態 | 意味 | 可能な操作 |
|---|---|---|
| `Draft` | 作成中。違反を保持できる | 割当の追加・削除、検査、確定 |
| `Confirmed` | 確定済み。変更不可 | 確定取消 |

`Draft` から `Confirmed` への遷移条件は「違反0件」（R-11）。
`Confirmed` から `Draft` へは確定取消で戻れる。取消の権限は店長のみ。

状態遷移図は [diagrams.md](./diagrams.md) を参照。

## 7. シナリオパターン

### S-01 正常系: 希望提出から確定まで

1. 店長が対象期間 2026-10-01〜2026-10-15 のシフト表を作成する（`Draft`）
2. スタッフ5名がそれぞれ希望を提出する（締切前）
3. 締切到来
4. 店長が希望をもとに割当を追加していく
5. 店長が検査を実行 → 違反0件
6. 店長が確定 → `Confirmed`、`ShiftScheduleConfirmed` を発行

### S-02 締切後の希望提出

1. スタッフが締切を過ぎてから希望を提出しようとする
2. `ShiftRequest` が R-09 により拒否
3. 期待結果: 提出は失敗し、シフト表の状態は変わらない

### S-03 18歳未満を深夜番に割当

1. 店長が17歳のスタッフを深夜番に割り当てる
2. 割当自体は成功する（`Draft` は違反を保持できる）
3. 検査を実行 → R-01 の違反が1件返る
4. 確定を試みる → R-11 により失敗
5. 期待結果: 違反内容が対象日・枠・スタッフとともに店長に提示される

割当の時点で例外を投げない設計にしている理由: 店長は複数の割当をまとめて操作する。
1件ごとに弾くと「一時的に違反しているが、次の操作で解消される」編集ができない。
違反は状態として保持し、確定というゲートで閉め出す。

### S-04 最低人数を満たさない

1. 深夜番に1名しか割り当てられていない日がある
2. 検査を実行 → R-05 の違反が返る
3. 確定を試みる → 失敗
4. 期待結果: 不足している日と枠、必要人数と現在人数が示される

### S-05 週40時間超過

1. あるスタッフが1週間に8枠（48時間相当）割り当てられている
2. 検査を実行 → R-02 の違反が返る
3. 期待結果: 対象スタッフ、対象週、合計時間が示される

週の範囲が対象期間の境界をまたぐケース（10/15が水曜の場合など）は、
対象期間内の割当のみで計算する。前後期間との合算は本スコープでは扱わない。
この単純化は既知の制限として記録する。

### S-06 希望外の枠への割当

1. 店長がスタッフの希望にない枠へ割り当てる
2. 検査を実行 → R-08 の違反が返る
3. 期待結果: 該当スタッフの希望と実際の割当の差分が示される

### S-07 確定済みシフトの変更試行

1. 確定済みのシフト表に割当を追加しようとする
2. R-10 により拒否される（例外）
3. 期待結果: 操作は失敗。変更するには確定取消が必要

### S-08 確定取消して再編集

1. 確定済みのシフト表を店長が取り消す → `Draft` に戻り `ShiftScheduleUnconfirmed` 発行
2. 割当を修正する
3. 再度検査・確定する

## 8. 既知の制限

| 制限 | 理由 | 将来の対応 |
|---|---|---|
| 週40時間の計算が対象期間内に閉じる | 前後期間の参照は集約をまたぐ | 集約をまたぐ読み取りモデルを導入する |
| 連続勤務日数の計算も同様に期間内で閉じる | 同上 | 同上 |
| 単一店舗のみ | ヘルプ勤務はスコープ外 | 店舗をまたぐ集約の設計が別途必要 |
| 自動割当なし | 最適化はDDDの学習対象外 | ドメインサービスとして追加可能 |
| 深夜割増の金額計算なし | 給与コンテキストの責務 | 別コンテキストとして分離 |
